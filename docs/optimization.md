# Оптимизация сцены: Blender → мобильный GLB

Практическое руководство под сцену масштаба «полуостров + два парка с детализацией».
Цель — открывать её на смартфоне, ничего не удаляя из проекта.

Цифры в таблицах — ориентиры для среднего телефона 2023–2025 годов (4–8 ГБ RAM,
мобильный GPU уровня Adreno 6xx / Apple A14). Это не догма, а точка отсчёта.

---

## 0. Сначала измерьте, потом решайте

```bash
node tools/glb-report.mjs сцена.glb
```

Отчёт покажет:

- сколько треугольников и вершин;
- сколько весят текстуры, геометрия, анимации;
- сколько draw call;
- какие расширения сжатия уже применены;
- сколько узлов можно схлопнуть в инстансы.

**Типичная картина для вашего случая:** 60–80% веса — текстуры (PNG/JPEG в
исходном разрешении), и отдельно десятки тысяч draw call из-за отдельных объектов.
Разбираться нужно в этом порядке: draw call → текстуры → треугольники.

Заодно проверьте на телефоне после загрузки, в консоли браузера:

```js
window.__nomaDebug.stats()
// { drawCalls, triangles, geometries, textures, programs, pixelRatio, zone }
```

Это то, что реально уходит на GPU в текущем кадре. Именно эти числа нужно уменьшать.

## 1. Бюджет для смартфона

| Показатель | Комфортно | Терпимо | Плохо |
|---|---|---|---|
| Draw call в кадре | < 150 | 150–500 | > 800 |
| Треугольников в кадре | < 300 тыс. | 300 тыс. – 1 млн | > 1.5 млн |
| Всего треугольников загружено | < 3 млн | 3–8 млн | > 10 млн |
| Вес GLB на зону | < 20 МБ | 20–50 МБ | > 60 МБ |
| Текстур в памяти GPU | < 250 МБ | 250–500 МБ | > 500 МБ |
| Разрешение текстуры | ≤ 1024 | 2048 | 4096 |

> **Ключевое правило:** телефон тормозит не от числа треугольников, а от
> **draw call** и от **overdraw** (перерисовки одних и тех же пикселей, типично
> для листвы и цветов с прозрачностью). 200 тысяч треугольников одним мешем
> работают быстрее, чем 5 тысяч треугольников в 2000 отдельных объектах.

---

## 2. Draw call: главный враг

Каждый отдельный объект Blender → отдельный draw call в three.js.
Дерево, скамейка, урна, светильник, клумба — каждый со своим вызовом.

### 2.1. Дублирующиеся объекты → Linked Duplicates (Alt+D)

В Blender копируйте повторяющиеся объекты через **Alt+D**, а не Shift+D.
`Alt+D` создаёт связанную копию: в GLB попадает один меш и много узлов, которые
на него ссылаются.

NOMA уже умеет превращать это в `InstancedMesh` — функция `mergeInstances()` в
`index.html` срабатывает при загрузке модели и группирует меши с одинаковой
геометрией и материалом. Но она работает только если геометрия **буквально одна
и та же** (один bufferView), а не «похожая».

Что это даёт: 1000 деревьев → 1 draw call вместо 1000.

### 2.2. Разная геометрия с общим материалом → Join (Ctrl+J)

Если объекты разные, но материал один (например, все скамейки с разной
конфигурацией, или вся мостовая), выделите их и нажмите **Ctrl+J**.
Получится один объект с одним материалом — один draw call.

Визуально результат идентичен. Это не удаление, а объединение.

### 2.3. Сколько материалов — столько draw call на зону

Проверьте материалы: `node tools/glb-report.mjs` покажет разбивку треугольников
по материалам. Если материалов 40 — будет минимум 40 draw call на зону, даже
после Join.

Сведите к 5–10 материалам на зону. Варианты:

- общий PBR-материал с текстурным атласом;
- одинаковые параметры (roughness, metallic) у похожих поверхностей;
- убрать уникальные материалы у мелких объектов (МАФ, урны) — заменить на
  общий «городской» материал с атласом.

## 3. Листва и цветы: overdraw

Это отдельная проблема, важнее треугольников.

Полупрозрачные плоскости с alpha test (листья, цветы, кусты) на мобильном GPU
дороги: каждый пиксель перерисовывается многократно, а alpha test отключает
раннюю отбраковку глубины.

Что помогает, не удаляя растительность:

1. **Alpha Clip вместо Alpha Blend.** В Blender для листвы используйте
   `Alpha Clip` (не `Blend`) — three.js получит `alphaTest`, а не
   `transparent: true`. Это заметно дешевле и не требует сортировки.
2. **Texture atlas + одна плоскость на куст** вместо 20 отдельных листиков.
3. **Меньше слоёв.** Куст из 3 пересекающихся плоскостей выглядит почти так же,
   как из 12, но стоит вчетверо дешевле.
4. **Отключить тени от листвы.** `castShadow = false` для мелкой растительности
   экономит целый проход рендера теней.
5. **Mip-карты и правильный alpha cutoff** (обычно 0.3–0.5): без мипов листва
   мерцает и требует больше сэмплов.

## 4. Текстуры: обычно 60–80% веса

### 4.1. Разрешение

Ревизия по типам:

| Что | Разрешение | Комментарий |
|---|---|---|
| Земля, мостовая, газон (tiling) | 1024 | повторяется, больше не нужно |
| Фасады зданий | 1024–2048 | 2048 только для главного корпуса |
| Листва, цветы | 512–1024 | с atlas |
| Мелкие МАФ, урны, скамейки | 256–512 | чаще всего различий не видно |
| Нормали для мелочи | не нужны | плоские поверхности |
| AO/roughness/metallic | 512–1024 | обычно можно упаковать в одну карту |

### 4.2. Формат: KTX2 (Basis Universal)

PNG и JPEG в браузере распаковываются в **несжатый** формат GPU: текстура
4096×4096 RGBA занимает 64 МБ видеопамяти независимо от того, что JPEG весил
500 КБ. На телефоне это главная причина падений.

KTX2 с Basis хранит текстуру в сжатом виде **прямо в GPU**:

- 4096×4096 в ETC1S/ASTC ≈ 8–16 МБ вместо 64 МБ;
- декодируется на GPU, не в JS;
- three.js уже подключён: `KTX2Loader` с `LIBS + 'basis/'` в `index.html`.

Для фотореалистичных albedo лучше **UASTC** (качество выше, вес больше),
для roughness/metallic/AO — **ETC1S** (сильнее сжатие, потери незаметны).

### 4.3. WebP как промежуточный вариант

Проще KTX2, поддерживается браузерами нативно, даёт 25–35% экономии против PNG.
Но в памяти GPU всё равно распаковывается целиком. Годится как быстрый шаг,
KTX2 — как правильное решение.

## 5. Геометрия без удаления объектов

Всё ниже сохраняет объекты и внешний вид, меняя только количество полигонов.

### 5.1. Merge by Distance (убрать дубли вершин)

`Mesh → Clean Up → Merge by Distance`, дистанция 0.0001–0.001.
На импортированных моделях часто убирает 10–30% вершин без визуальной разницы.

### 5.2. Limited Dissolve (упростить плоские поверхности)

`Mesh → Clean Up → Limited Dissolve`, угол 1–5°.
Стены, мостовая, газоны, крыши — тысячи лишних треугольников на плоскости
схлопываются в несколько. Визуально не отличается.

### 5.3. Decimate для дальних объектов

`Decimate (Collapse)` с ratio 0.3–0.5 для того, что зритель видит издалека
(дальние деревья, здания на периферии). Объект остаётся, просто легче.

Для архитектуры используйте `Decimate (Planar)` — он сохраняет прямые углы.

### 5.4. Убрать скрытые каналы

Часто в GLB уезжают лишние UV-наборы, второй цвет вершин, тангенты при
отсутствии normal map. Проверьте в отчёте: байт геометрии на треугольник
больше 100 — значит что-то лишнее.

В Blender: `Object Data → Geometry Data → Clear Custom Split Normals`,
удаление неиспользуемых UV-слоёв в `Object Data → UV Maps`.

## 6. Разбивка на зоны (обязательно для 1,8 ГБ)

1,8 ГБ целиком в память телефона не поместится никогда — независимо от сжатия.
Сцену нужно делить на зоны и подгружать по требованию. Поддержка уже есть.

### 6.1. Как делить в Blender

Логичное деление для вашего случая:

```
main.glb        полуостров: рельеф, дороги, дальние здания, силуэт   (лёгкий, всегда)
park-a.glb      первый парк с детализацией                          (грузится по клику)
park-b.glb      второй парк с детализацией                          (грузится по клику)
```

Экспорт: выделите объекты зоны → `File → Export → glTF` → включите
**Selected Objects**. Получите отдельный GLB на каждую зону.

Важно: **начало координат должно совпадать**. Не перемещайте объекты перед
экспортом зоны — иначе она встанет не на место. Проще всего держать одну сцену
Blender и экспортировать из неё разные наборы выделения.

### 6.2. Как подключить в tour.json

```json
"groups": [
  {
    "id": "park-a",
    "title": "Парк «Северный»",
    "model": "park-a.glb",
    "cam": { "p": [30, 18, 40], "t": [10, 2, 10] },
    "pois": ["fountain", "playground", "rosary"]
  },
  {
    "id": "park-b",
    "title": "Парк «Южный»",
    "model": "park-b.glb",
    "cam": { "p": [-40, 20, 10], "t": [-10, 2, 0] },
    "pois": ["amphitheatre"]
  }
]
```

Модель в `model` подгружается при выборе зоны и **выгружается** при переходе
на другую — геометрия и текстуры освобождаются (`dispose`). То есть в памяти
одновременно лежат базовая сцена и одна детальная зона, а не все три.

Переход на «Все» выгружает зону и возвращает базовую сцену.

### 6.3. Что кладётся в базовую сцену

- рельеф, вода, дорожно-тропиночная сеть;
- дальние и средние здания;
- деревья общего плана;
- то, что видно с обзорной точки.

Что кладётся в зону:

- детализация: цветы, МАФ, скамейки, светильники, урны;
- мелкие объекты, которые видно только вблизи.

Дерево издалека и то же дерево в парке — это два разных объекта с разной
детализацией. Визуально на расстоянии разницы не видно, а вблизи работает
детальная версия. Это LOD на уровне зон, а не упрощение сцены.

## 7. Готовый пайплайн сжатия

Нужен Node.js. Один раз:

```bash
npm install -g @gltf-transform/cli
```

### 7.1. Обычная обработка (meshopt)

```bash
gltf-transform optimize in.glb out.glb \
  --compress meshopt \
  --texture-compress webp \
  --texture-size 2048 \
  --simplify false
```

`--simplify false` — важно: не хотим, чтобы инструмент сам упрощал геометрию.
Форму контролируете вы в Blender.

### 7.2. С KTX2 (лучший результат для телефона)

```bash
gltf-transform etc1s in.glb out.glb --quality 200
# или, если нужен фотореализм:
gltf-transform uastc in.glb out.glb --level 2 --rdo-quality 3
```

### 7.3. Почему meshopt, а не Draco

| | Draco | Meshopt |
|---|---|---|
| Вес файла | меньше | немного больше |
| Размер декодера | ~200–800 КБ | ~30 КБ |
| Скорость декодирования | медленнее, на главном потоке JS | быстрее, с распаковкой в фоне |
| На слабом телефоне | заметная пауза при загрузке | почти незаметно |

Для мобильных туров meshopt обычно выигрывает: файл чуть больше, но загрузка
гладкая. Draco имеет смысл для очень больших сцен при быстром канале.

Оба декодера уже подключены в `index.html` (`DRACOLoader`, `MeshoptDecoder`),
так что можно использовать любой без правок кода.

## 8. Проверка результата

После каждого шага:

```bash
# 1. Что стало с файлом
node tools/glb-report.mjs out.glb

# 2. Открыть тур и посмотреть в консоли браузера
window.__nomaDebug.stats()
```

Целевые значения — из таблицы в разделе 1. Если draw call всё ещё в тысячах,
возвращайтесь к разделу 2 (инстансы и Join). Если вес в текстурах — к разделу 4.

Проверять нужно **на реальном телефоне**, не только в эмуляторе десктопного
браузера: у мобильного GPU другие лимиты по памяти и заполнению.

## 9. Порядок работ для вашей сцены

1. Прогнать `tools/glb-report.mjs` на текущем экспорте — увидеть, что тяжелее.
2. Свести материалы к 5–10 на зону.
3. Все повторяющиеся объекты — через `Alt+D` (связанные дубликаты).
4. Разную геометрию с общим материалом — `Ctrl+J`.
5. `Merge by Distance` + `Limited Dissolve` по всей сцене.
6. Разделить на `main.glb` + `park-a.glb` + `park-b.glb` по коллекциям.
7. Текстуры: понизить разрешения по таблице 4.1, листву — на атлас.
8. Прогнать каждый файл через `gltf-transform optimize` (meshopt + webp/KTX2).
9. Прописать зоны в `tour.json` (`groups[].model`).
10. Проверить `window.__nomaDebug.stats()` на телефоне, сравнить с бюджетом.

Что даёт какой эффект (порядок величины на типичной сцене такого масштаба):

| Шаг | Эффект |
|---|---|
| Инстансы вместо копий | draw call в 5–50 раз меньше |
| Join по материалу | draw call в 2–5 раз меньше |
| Merge by Distance + Limited Dissolve | треугольники −20–40% |
| Текстуры 4096 → 1024 + KTX2 | память GPU в 4–8 раз меньше |
| meshopt | вес файла в 2–4 раза меньше |
| Разбивка на зоны | в памяти телефона 1 зона вместо всей сцены |

Суммарно 1,8 ГБ превращаются в 40–120 МБ на зону при сохранении всей
детализации — но только если пройдены все шаги, а не один.

---

## 10. Чего делать не нужно

- **Не удаляйте объекты** ради экономии — на масштабе вашей сцены это даст
  меньше, чем инстансы и текстуры.
- **Не включайте Draco и KTX2 одновременно без проверки** — суммарный вес
  декодеров и время распаковки могут съесть выигрыш на слабом телефоне.
- **Не ставьте LOD «на глазок»** без замера — неправильные пороги заметны
  как «прыжки» геометрии.
- **Не делайте 4096-текстуры «на всякий случай»** — на телефоне это прямой
  путь к потере WebGL-контекста.
